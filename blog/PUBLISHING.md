# Blog Publishing Workflow — oilrigsnow.com

Two content tracks live in the same `/blog/` hub, tagged separately:

- **`market-watch`** — new rig/equipment availability. Published only when
  something genuinely new exists. No fixed cadence, no filler. **Never
  names the specific company/seller or specific yard/town.** Rig type,
  spec class, and broad region (e.g. "Permian Basin") are fine. Goal:
  tease that inventory exists and drive the reader to contact ORN or
  check 2tds.us. Sanitization checklist lives in `blog/_drafts/CHECKLIST.md`.
- **`industry-news`** — monthly general industry roundup (rig counts, EIA
  data, equipment sales/auctions, capex, regulatory/tariff, M&A). Same
  sourcing discipline as the existing posts: cited inline, no invented
  figures.

## MANDATORY: Mike approves every post before it goes live. No exceptions.

This is enforced structurally, not just by process discipline:

1. **All work happens on the `blog-drafts` branch**, never directly on
   `main`. `main` is the production branch Cloudflare Pages deploys to
   `oilrigsnow.com` — that binding is dashboard-level Cloudflare Pages
   config, not something a commit can bypass.
2. Cloudflare Pages auto-builds **every** branch pushed to the repo, but
   only `main`'s build is served at the `oilrigsnow.com` custom domain.
   Non-production branches get a `<hash>.oilrigsnow-com.pages.dev`
   preview URL instead — visible for review, invisible to the public
   domain, not indexed (no canonical points there, and it's a
   throwaway subdomain search engines don't associate with the site).
3. Draft posts and any `posts.json` / RSS / sitemap changes for them
   land as commits on `blog-drafts`. **Do not** merge or push to `main`.
4. When a draft is ready, open a PR from `blog-drafts` → `main` (or
   message Mike directly with the preview URL + PR link — either
   channel works, PR is the audit trail). Mike reviews the live preview
   URL and the diff.
5. **Only Mike merges the PR to `main`.** That merge is the publish
   action — it is the only path that updates the production branch and
   therefore the only path that changes what `oilrigsnow.com` serves.
   No agent merges `blog-drafts` → `main` on its own authority, ever.
6. After merge, Cloudflare Pages redeploys `main` automatically (usually
   under 90s) and the post goes live.

This means "staged until approved" isn't a documented convention that a
future agent could accidentally skip — it's the actual Cloudflare Pages
production-branch binding. Committing straight to `main` is the only way
to bypass review, and doing that without Mike's explicit go-ahead
violates this workflow.

## Step by step: adding a new post

1. Checkout/create the `blog-drafts` branch (branch off current `main`
   if `blog-drafts` doesn't exist yet or is stale).
2. Write the post HTML at `blog/<slug>/index.html`, following the
   existing post template (title/meta/OG/Twitter/JSON-LD Article +
   BreadcrumbList, same visual system as `blog/index.html`). Sourcing
   discipline: cite inline, no invented figures — same bar as the two
   existing posts.
3. If tagged `market-watch`, run it through the sanitization checklist
   in `blog/_drafts/CHECKLIST.md` before it's considered draft-ready —
   no company/seller name, no specific yard/town.
4. Add an entry to `blog/posts.json` (slug, title, description, tags,
   published date).
5. Run the build tool to regenerate the hub card, RSS feeds (all +
   per-tag), and the blog `<url>` entries in `sitemap.xml`:
   ```
   python3 _tools/blog_build.py --posts blog/posts.json \
     --sitemap sitemap.xml --out-dir /tmp/blog-out
   ```
   Copy the generated `rss.xml`, `rss-market-watch.xml`,
   `rss-industry-news.xml` into `blog/`, and the generated `sitemap.xml`
   to the repo root. Update `blog/index.html`'s post-card grid to match
   `posts.json` (the build tool documents the exact card markup; keep it
   manual/reviewable rather than templated at request time so Mike's
   diff review is a real diff of real HTML).
6. Commit everything to `blog-drafts`.
7. Push, get the Cloudflare Pages preview URL (check the Pages project
   dashboard or the GitHub commit's deployment status check), and hand
   the preview link to Mike for review.
8. Mike approves → PR merged to `main` by Mike → live within ~90s.
   Mike requests changes → iterate on `blog-drafts`, no re-approval
   needed until the next review pass.

## Ongoing sitemap maintenance

`sitemap.xml`'s blog section is **not edited by hand** past this point —
it's regenerated by `_tools/blog_build.py` from `posts.json` every time a
post is added, so it can never drift out of sync. The script only
touches `<url>` blocks whose `<loc>` starts with
`https://oilrigsnow.com/blog/`; every other sitemap entry (homepage,
category hubs, legal pages, etc.) passes through untouched.

## RSS feeds

- `/blog/rss.xml` — every published post, newest first.
- `/blog/rss-market-watch.xml` — Market Watch posts only.
- `/blog/rss-industry-news.xml` — Industry News posts only.

All three are regenerated by the same build step and referenced via
`<link rel="alternate" type="application/rss+xml">` in `blog/index.html`
for feed-reader autodiscovery.
